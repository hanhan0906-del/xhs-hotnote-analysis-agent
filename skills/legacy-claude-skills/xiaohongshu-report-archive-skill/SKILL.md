# 小红书分析报告归档 Skill

## 概述

`xiaohongshu-account-analysis` skill 产出的账号分析报告里，模块三/四/五分别沉淀了选题、标题、封面三类可复用规律。本 skill 把这些规律从报告正文里"拆出来"，逐条整理成独立 md 文件，归档进对应知识库，方便以后跨账号横向查阅、复用，不用每次都翻旧报告。

**标签不入库**：标签这类内容要根据用户自己的原创资料现场生成，且刻意要求每篇笔记标签都不一样，不存在"可复用公式"这个概念，跟标题/选题/封面的性质不同，所以不设标签库。

单账号分析报告本身**不做**跨账号比较（见 xiaohongshu-account-analysis 的写作规则），跨账号沉淀和验证状态升级，是本 skill 的职责。

## 归档清单（去重判重用）

清单文件：`references/archived_manifest.json`（本 skill 目录下，不存在则视为空，首次运行创建）

结构：
```json
{
  "reports": [
    {
      "report_path": "C:\\...\\对标分析_程程老师厚德载物.md",
      "account_name": "程程老师厚德载物",
      "archived_at": "2026-07-14",
      "entries_written": [
        "标题库/2小时足够了系列.md",
        "选题库/K12资料电商-年级选择影响天花板.md",
        "封面模版库/类型1-浅蓝渐变粉字块.md"
      ]
    }
  ]
}
```

**执行逻辑：**
1. 用户给出报告路径 → 检查该 `report_path` 是否已在清单里
2. 已归档过：提示用户"该报告已于[日期]归档过，是否重新归档（会触发合并/覆盖逻辑）"，用户确认后再继续
3. 归档完成后，把本次写入/更新的所有条目路径记入清单（若报告已存在则覆盖该条目）

## 每条库目标条目的统一格式

不管归到哪个库，条目内部结构统一（封面库额外带图）：

```markdown
# [规律名称]

**类型：** 标题公式 / 选题判断 / 封面类型
**赛道：** [从报告"赛道"字段抄，如"K12资料电商"]
**来源账号：** 账号A（2026-07-13分析）
**验证状态：** 🔶 单账号，待验证

**公式/内容：**
```
[具体公式、结构、模板]
```

**适用条件/限定：**
[从报告里"关键发现""不能简单归因""仅本账号成立"这类限定语句提炼，没有就写"报告未明确限定条件"]

**代表数据：**
[账号A：点赞xxx，示例"xxx"]

**同源笔记完整信息（组合搭配时参考）：**
[针对"代表数据"里提到的那条具体代表笔记（不是整个赛道/整个账号），回填它完整的四件套原貌，让以后跨库调用组合时能看到这条内容原本搭配的是什么，避免把不同调性的标题/封面/标签硬拼在一起。如果代表数据引用了多条笔记，每条笔记单独列一个小节。]
- 标题原文：[完整标题，不是提炼后的公式]
- 封面类型：[[对应封面库条目]]（如果这条笔记的封面也单独入库了，双向链接；没入库就写"未单独入库，风格参考：xxx"）
- 正文风格：[一句话摘要，如"极简清单型，258字"，不放正文全文]
- 点赞：[数据]

---
*首次归档：2026-07-14，来源报告：对标分析_账号A.md*
```

**为什么加这个字段：** 库是按"标题/选题/标签/封面"四个维度分开存的，方便按需查找，但也导致"这条标题原本配的是什么封面"这层关联丢失了。以后从多个库分别挑内容拼成一篇新笔记时，如果不知道各自的原始搭配，容易出现"最强封面+完全不搭调的标题风格"这种拼接感。这个字段不要求以后使用时必须原样搬全套，而是让调用者能看到"原装搭配长什么样"，自己判断是要保持统一风格照搬，还是有意打散重组。

**合并已有条目时**（发现新报告的规律和库里已有条目高度相似）：
- 保留原文件名和首次归档信息不变
- "来源账号"改为列表，追加新账号
- "验证状态"从 🔶单账号 升级为 ✅N个账号验证
- "代表数据"追加新账号的数据
- "适用条件/限定"如果新报告有不同/矛盾的限定条件，两条都保留并注明"账号A显示X，账号B显示Y，暂不确定哪个更普遍"，不要为了合并而抹掉差异

**判断"是否高度相似"的标准：** 核心公式结构相同（比如都是"极短时间承诺+具体分数"类标题），不要求文字完全一致。拿不准时倾向于**不合并**、新建条目，并在两条里互相标注"参见[[另一条]]，规律相近待观察"——防止把两个实际不同的规律强行捏合导致信息丢失。

## 执行流程

### Step 1：读取报告，定位可抽取内容

读取报告 md 全文，重点解析：
- 文件头：账号名、分析日期、赛道
- 模块三（选题分析）：选题类型表格 + 该模块下的"关键发现"文字
- 模块四（标题公式）：各标题系列表格 + 具体公式模板 + 特征说明
- 模块五 5.1（封面公式）：各封面类型描述 + 报告 `_assets/` 文件夹里对应的图片文件

**跳过规则：** 如果某模块在报告里写了"数据不足，本模块跳过"或"无显著规律，本小节从简"，对应库不产出新条目，不要为了凑数硬提炼。

### Step 2：逐类型提炼成独立规律条目

原则：**提炼判断规律，不要照抄原始数据表格**。

- 选题：不是把"五下13条平均288.5赞"这行数据搬进选题库，而是提炼成"[规律名称]：年级/科目选择对天花板影响可达N倍"这样的可复用判断，数据作为佐证放在"代表数据"里
- 标题：每个独立标题系列（报告模块四表格里的一行）提炼一条，公式模板抄报告里已经写好的"可复用标题公式模板"部分
- 封面：每个封面类型一条，文件名用**数字编号**（类型1/类型2/类型3...），不用字母——账号一多，A-Z 26个很快用完。注意报告原文里可能仍用 A型/B型 这种字母描述（取决于分析报告本身用的命名），归档时统一转换成数字编号，不要把字母原样搬进库里。图片从报告同目录的 `[报告文件名]_assets/` 文件夹复制

对每条提炼结果，同时摘录报告里紧邻的限定/警示性文字（"仅本账号成立""不能简单归因""样本少"），写入"适用条件/限定"字段，**不能只抄结论不抄限定**。

### Step 3：封面条目的图片处理

```python
import shutil, os

def archive_cover_image(report_assets_dir, image_filename, library_dir):
    """把报告assets里的代表图复制到封面库统一的图片文件夹"""
    images_dir = os.path.join(library_dir, "图片")
    os.makedirs(images_dir, exist_ok=True)
    src = os.path.join(report_assets_dir, image_filename)
    dst = os.path.join(images_dir, image_filename)
    if os.path.exists(src):
        shutil.copy2(src, dst)
        return dst
    return None
```

封面库条目结构：`封面模版库/[类型名].md`（类型名用数字编号，如"类型1-浅蓝渐变粉字块"），图片统一放在 `封面模版库/图片/` 这一个共享文件夹里（不是每条一个子文件夹，也不和 md 文件混在根目录）。

md 里嵌入图片时**用 Obsidian 的宽度语法缩小尺寸**，不要用默认全尺寸（原图直接嵌入在报告里观感很大）：
```
![封面说明|300](图片/cover_A_top_2447.jpg)
```
`|300` 表示显示宽度300px，这个尺寸已确认合适，不用再调。

**单条只有1张代表图** → 直接嵌入即可。
**单条有2张（或以上）代表图需要对比**（如同一类型的最高赞vs最低赞）→ 用 Markdown 表格把图片放进并列单元格，横向对比展示，不要竖着连续堆两张大图：
```
| 点赞2447（全账号最高） | 点赞3（全账号最低） |
|---|---|
| ![封面-2447赞\|300](图片/cover_A_top_2447.jpg) | ![封面-3赞\|300](图片/cover_A_bottom_3.jpg) |
```

只存**代表性截图**（该类型的典型例子，通常1-2张），不搬运报告里的全部图。图片文件名沿用报告里的原名（如 `cover_A_top_2447.jpg`），如与库里已有文件重名，加账号名前缀区分。

### Step 4：查重与合并

对每条待写入的规律，在对应库目录下用**关键词/结构相似度**粗筛已有 md 文件（读文件名 + 各文件"公式/内容"字段），判断是否命中"高度相似"标准（见上文）。

- 命中 → 按"合并已有条目"规则更新该文件
- 未命中 → 新建文件

### Step 5：写入清单

完成本次报告的全部归档后，更新 `references/archived_manifest.json`（见"归档清单"一节）。

---

## 输出确认

归档完成后，向用户汇报本次写入/合并的条目清单（每条注明"新建"还是"合并到已有"），不需要用户手动检查文件本身，但要让用户知道具体动了库里哪些文件，方便随时回滚。

## 已知待调整项（首次使用后与用户一起校准）

- 相似度判断目前依赖人工读取判断，尚无量化规则，第一次实际归档后根据效果调整判断标准的宽严
- 选题库的"规律"抽象粒度（按赛道？按年级/科目维度？）需要归档几篇不同赛道的报告后才能看出合适的分类方式
